# 자동 업데이트 준비 상태 (2026-10-30)

PR #1 / codex/approved-windows-releases. 기존 원격 6379664 대비 로컬 수정 6개와
신규 check_full_launcher.py를 보존한 뒤 abe9ee1에 커밋했다. 원래 홈/팝업 디자인은
변경하지 않았다. v0.0.3은 출시 **후보**이며 실제 번호는 사용자가 최종 승인한다.

## 온라인 확인 실패 원인

설치된 v0.0.1의 실제 unified_updater를 읽기 전용으로 실행했다(pycache 생성 금지).
동일 코드가 제한된 실행 환경에서는 URLError / Errno 11001 getaddrinfo failed,
네트워크 허용 환경에서는 app=0.0.1, launcher=None을 반환했다.
앞선 복사본 화면의 확인 실패는 재현된 DNS 제한에 부합하며, Release 없음과 다르다.
이 결과로 모든 사용자 PC의 네트워크 정상까지 보장하지는 않는다.

공개 Release 및 원격 태그 확인: tracker-v0.0.1, v9.0.0만 존재.
launcher-v0.0.3 태그 충돌 없음. 새 런처 미게시 상태는 정상적인 업데이트 없음이다.
후보 소스에서는 DNS/연결 실패, API 한도 초과, 권한 거부를 서로 다른 오류 문구로
구분한다. 실패를 업데이트 없음으로 바꾸거나 TLS 검증을 우회하지 않는다.
빈 Release 목록과 DNS/403/429 분류 회귀 테스트 3개 통과.

## 실제 설치본의 임시 복사 검증

대상: 기존 조사한 v0.0.1 완성 설치 폴더. 원본 246개 파일 전후 SHA 동일.
수정 호스트는 임시 복사본에만 적용했고 검증 후 자식 프로세스를 종료하고 복사본을 정리했다.

검증 제품 커밋: abe9ee1d02524f69191b32406c79e8db6d896f6a
로컬 v0.0.3 ZIP SHA-256:
78e04820fe82b7ce7b682b0afd348e304c6dcd111c1317413e976d4f1d030d00
로컬 결과는 CI artifact의 다운로드 검증을 대신하지 않는다.

| 항목 | 결과 |
|---|---|
| v0.0.1 실제 업데이터 → v0.0.3 전체 패키지 | 외부/내부 SHA 검증 및 설치 성공 |
| 수정 호스트 → 실제 전체 런처 | pythonw 자식 실행, healthy 완료, 홈 화면 육안 확인 |
| 온라인 조회 | 전체 UI에서 최신 버전 표시, 기록기 0.0.1 / 런처 0.0.3 독립 표시 |
| 시작 실패(임시 entrypoint exit 7) | 다음 호스트 호출에서 실제 v0.0.1 UI 프로세스 정상 시작 |
| healthy 전 강제 종료 | 다음 호스트 호출에서 실제 v0.0.1 정상 시작 |
| healthy 후 강제 종료 | 현재 버전 유지. 자동 복구 지원하지 않음 |
| 잘못된 해시 | 거부, 기존 활성 상태 유지 |
| 추출 중단 | 기존 활성 상태 유지, stage 정리 |
| 복사본 기록/설정/배경 보존 | 변경 host/runtime 제외 기존 244개 파일 SHA 동일 |
| 8.x/9.x → 0.x | 구성요소별 정책, 실제 후보 ZIP 설치, 수동 복귀, v 접두사 경로 포함 6개 회귀 테스트 통과 |

check_full_launcher.py는 설치 API와 host.main을 호출한다. Popen 관찰 wrapper는
실제 실행 인수/환경/진입점을 그대로 사용하고 실제 자식 프로세스를 종료·대기한다.
이는 게시된 새 Release를 UI에서 클릭해 내려받는 end-to-end 검증은 아니다.
네트워크 해시 다운로드 테스트는 메모리 응답 사용 범위를 별도로 구분한다.
이미 통과한 v0.0.2 전체 UI 검증 후, 변경된 후보 v0.0.3 경로만 추가 검증했다.

## 최초 1회 호스트 전환 절차 — 사용자 승인 전 실행 금지

현재 원본 호스트는 launcher 모듈 충돌로 pending 저장에 실패한다.
일반 런처 ZIP은 host/BAT/VBS를 포함하지 않으므로 새 Release만 게시해서 해결되지 않는다.

1. 실제 사용 바로가기의 설치 루트를 확정하고 런처/기록기를 종료한다. 원본 runtime,
   host, 실행 BAT/VBS, 설정과 user_data를 설치 밖 별도 백업 위치에 복사하고 해시를 기록한다.
2. 사용자가 승인한 고정 CI 커밋의 bootstrap artifact와 SHA를 검증한다. ZIP 전체를
   사용자 루트에 풀지 말고 별도 staging에서 검사한다. 이번 수정에 필요한 파일은
   launch_host.pyw뿐이다. BAT/VBS는 현재 Python 경로를 보존하고 변경이 필요하면 별도 검토한다.
3. 원본 호스트를 백업한 상태에서 같은 볼륨의 임시 파일 → 원자적 교체로 수정 호스트를
   적용한다. 사용자 기록, 설정, versions, launcher_versions는 이동/삭제하지 않는다.
4. 기존 0.0.1이 새 호스트로 정상 시작하는지 먼저 확인한다. 실패하면 새 런처 설치를
   진행하지 말고 백업 호스트/runtime만 복원한다. 검증된 백업을 덮어쓰지 않는다.
5. 승인된 새 런처 패키지를 기존 업데이터로 설치하고 호스트 재시작/healthy를 확인한다.
   실패하면 다음 호스트 실행의 이전 버전 복구를 확인한다. 필요시 종료 후 백업 runtime을
   복원하며 사용자 데이터와 기존 버전 폴더는 그대로 둔다.
6. 기존 기록·설정·배경 해시와 화면 읽기를 확인한 후 전환 완료 증빙을 남긴다.

이 절차는 설계이며 실제 사용자 설치에 적용하지 않았다. 자동 bootstrap 설치기는 없다.
8.x/9.x의 구형 업데이터는 0.x를 자동 선택하지 못할 수 있어, 동일한 승인 전환 단계에서
새 업데이터를 먼저 설치해야 한다. 새 코드의 버전 정책 테스트 통과와 구형 코드의 자체
전환 능력은 별개다. 향후 8/9 major는 구형 계열로 예약된다.

## 출시 후보와 남은 차단

v0.0.3 유지 권고: 제공된 v0.0.2 소스와 수정본을 명확히 구분하고 기존 0.0.2 설치에도
후속 버전이 된다. 공개 태그 충돌은 없으나 외부에 배포한 모든 ZIP을 조사한 것은 아니다.
기록기는 0.0.1 유지하며 재게시하지 않는다. launcher-v0.0.3 / tracker-vX.Y.Z 독립 관리.

실제 자동 업데이트 가능 여부: **전환된 호스트 + 승인된 새 Release가 갖춰진 설치에 한해
가능하도록 구현·부분 검증됨. 현재 원본 설치에는 새 Release만으로 안전한 자동 전환 불가.**

pending 유지 사유:
- 실제 사용 경로 확인 및 최초 호스트 전환 실행은 사용자 승인 전 보류.
- 게시될 정확한 CI artifact를 사용한 발견→완료 팝업→재시작 전체 클릭 흐름 미완료.
- healthy 이후 강제 종료 자동 롤백은 지원하지 않음. 요구 범위 합의 또는 추가 구현 필요.
- 실제 기록기 UI에서 개인 기록을 읽고 확인하는 작업은 수행하지 않음(바이트 보존은 확인).

위 항목을 검증/합의한 비식별 증빙과 사용자 검토 없이 verified로 전환하지 않는다.
main 병합과 Release 게시는 수행하지 않았다. 승인 후에는 main CI 성공 artifact의
run ID/source SHA/ZIP SHA를 고정한 요청을 승인하고 수동 Release workflow를 실행한 뒤
production-release 환경에서 소유자가 승인한다. launcher latest=false를 권고한다.
