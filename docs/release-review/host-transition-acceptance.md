## 재사용한 격리 시험과 남은 범위

[기존 GUI 증빙](../ARTIFACT_GUI_RESULTS.md)의 실제 Actions artifact 다운로드,
해시/manifest 검증, 발견→설치→완료→재시작→healthy, 손상 거부, 시작 실패 후
다음 실행의 이전 버전 복구, 파일 바이트 보존 결과를 재사용한다.
시험 런처 ZIP SHA-256은 2284b0a 후보와 동일하다:
78e04820fe82b7ce7b682b0afd348e304c6dcd111c1317413e976d4f1d030d00.
8.x/9.x→0.x의 구성요소별 버전 정책은 기존 회귀 증빙 범위다.

- healthy 이후 충돌/강제 종료는 자동 롤백하지 않는다. healthy 이전 실패도
  같은 실행에서 자동 재시작하는 것이 아니라 다음 호스트 실행에서 이전 버전을 선택한다.
- 공개 Release의 실제 발견·다운로드 경로는 artifact 시험과 다르며 아직 미검증이다.
  게시 후 별도 승인된 확인에서 태그/첨부 SHA/발견/다운로드를 확인해야 한다.
  실제 v0.0.3 설치·재시작은 추가 설치 승인 없이는 수행하지 않는다.
- 네트워크 다운로드 중단 GUI 시험은 [별도 중단 증빙](../ARTIFACT_INTERRUPTION_RESULTS.md)으로
  완료했다. 실제 응답 일부 수신 후 연결 끊김 예외를 주입한 범위이며 모든 네트워크 장애의 보장은 아니다.
- 전원 차단·모든 디스크 장애·다른 PC의 Python/보안 프로그램/동기화 충돌은 보장하지 않는다.
  이번 한 설치본의 성공을 모든 사용자 환경의 성공으로 일반화하지 않는다.

## pending 해제 평가와 승인 순서

실제 최초 전환 및 기존 기록기 표시 확인이라는 선행 조건은 충족됐다.
그러나 공개 전달 경로 사후 확인 계획과 사용자 출시 승인이 남아 있으므로 pending 해제 조건이
전부 충족됐다고 판정하지 않는다. compatibility.json의 기존 reason은 이전 시점 기록이며
현재 완료 범위는 이 문서가 보완한다. 이번에는 그 파일을 변경하지 않는다.

1. 사용자가 v0.0.3 후보, healthy 이후 한계, 완료된 다운로드 중단 시험의 범위,
   공개 경로 사후 확인 계획과 수동 호스트 패키지 동봉 방식을 검토한다.
   한계 수용은 미검증 시험의 성공 처리가 아니다. 해결되지 않은 필수 조건이 있으면 pending 유지.
2. 승인된 출시 전 검증 범위가 충족된 경우에만 비식별 증빙을 연결하는 verified 전환과
   PR main 병합을 별도로 승인받는다. verified를 모든 장애/공개 전달 경로의 검증 완료로 해석하지 않는다.
3. 병합 후 main Windows CI의 정확한 source/run 및 두 ZIP SHA를 고정해 최종 게시 승인을 받는다.
   문서/manifest 변경으로 ZIP 해시가 달라질 수 있으므로 현재 branch ZIP을 최종본으로 간주하지 않는다.
4. 수동 Release workflow와 production-release 필수 승인 후 공개한다.
   사후 전달 경로 점검과 실제 설치 승인은 구분한다.

전체 순서는 [출시 절차](../LAUNCHER_RELEASE_PROCEDURE.md)를 따른다.
