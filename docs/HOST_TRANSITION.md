# 최초 1회 호스트 전환 패키지 — 검토용, 사용자 승인 전 실제 설치 금지

변경 파일은 설치 루트의 launch_host.pyw 한 개뿐이다. 알려진 v0.0.1 호스트 SHA와
현재 runtime=0.0.1, pending 없음, 이전 런처 진입점을 확인하고 적용한다.
기록·설정·배경·runtime·BAT/VBS·버전 폴더는 수정하지 않는다.
원본 호스트와 복구 영수증은 사용자가 지정한 별도 백업 폴더에 보존한다.
영수증에는 로컬 설치 경로가 들어 있으므로 GitHub에 올리지 않는다.

## 승인 후 사용자가 직접 할 일

1. 평소 사용하는 바로가기의 설치 루트를 확인한다. 런처와 기록기를 모두 종료한다.
   도구의 `--apps-closed`는 사용자 확인이며 프로세스를 자동 종료하거나 탐지하지 않는다.
2. 정식 사용자 배포는 공식 `launcher-v0.0.3` Release에 함께 첨부된
   `dokkaebi-host-transition.zip`을 받는다. 게시 전 검토자는 승인된 CI의
   `windows-bootstrap-<SHA>` artifact를 사용한다.
   ZIP SHA-256을 승인 기록의 값 및 .sha256과 비교한다. 동일 다운로드의 체크섬만으로
   배포자 신뢰가 생기는 것은 아니므로 GitHub 계정/저장소/run/커밋도 확인한다.
3. `dokkaebi-host-transition.zip`을 **설치 폴더 밖**의 새 폴더에 푼다.
   설치 폴더 위로 직접 압축을 풀지 않는다. 패키지 폴더에서 아래 명령을 실행한다.

```powershell
python host_transition.py inspect --root "<확인한 설치 루트>"
python host_transition.py apply --root "<확인한 설치 루트>" --backup "<기존에 없는 별도 백업 폴더>" --apps-closed
```

Python 3.12 사용. 백업 폴더의 부모는 미리 존재해야 한다. 기존 백업 폴더 재사용은
거부한다. 이미 같은 호스트면 쓰지 않는다. 알 수 없는 호스트, 링크/junction,
해시 불일치, pending 업데이트는 중단하고 원인을 검토한다.

4. 기존 BAT/VBS로 v0.0.1이 다시 열리는지 먼저 확인한다. 그 다음 승인된 런처 업데이트를
   설치하고 재시작한다. 기록과 설정을 확인한다. 실제 적용은 별도 최종 승인 후 진행한다.
5. 전환 직후 실패하면 앱을 닫고 아래 명령으로 **호스트만** 복원한다.

```powershell
python host_transition.py rollback --root "<동일 설치 루트>" --backup "<앞에서 만든 백업 폴더>" --apps-closed
```

원본 백업 SHA와 설치 루트, 현재 호스트 SHA를 확인한다. 다른 사람이 수정한 호스트를
덮어쓰지 않는다. 백업은 삭제하지 않는다. 런처 업데이트 이후 runtime까지 되돌리는
명령이 아니다. 새 런처 시작 실패는 수정 호스트의 다음 실행 복구를 먼저 사용한다.
원본 호스트로 복귀하면 기존 모듈 충돌도 돌아오므로 pending 상태에서 무작정 복원하지
말고 별도 복구 진단을 한다. 강제 전원 차단 후에는 영수증을 보존하고 inspect로 확인한다.

## 실제 온라인 업데이트 시험 설계 (아직 실행하지 않음)

**GitHub Actions 검토용 artifact를 사용한다.** 공개 저장소의 Draft Release를
접근 제어가 검증된 비공개 시험 환경으로 간주하지 않는다. 이번 작업에서는 Draft나
공개 Release를 만들지 않는다. 일반 런처는 Release API만 조회하므로 Actions artifact를
자동 발견하지 않는다. artifact가 반드시 비밀이라는 뜻은 아니며 사용자 데이터는 넣지 않는다.

다음 전용 시험 드라이버를 별도 구현·검토한 뒤 실행한다:

- 임시 복사본 루트만 허용하고 원본 루트/junction/symlink는 거부한다.
- 승인된 성공 CI run/source SHA/artifact ID와 archive digest를 고정한다. 로그인된
  GitHub CLI의 기존 인증으로 실제 artifact를 다운로드한다. 토큰을 제품 코드/설정에
  저장하지 않으며 인증 헤더를 Release 다운로드 주소로 전달하지 않는다.
- 다운로드한 외부 artifact archive와 내부 ZIP/sidecar/build-info의 버전·커밋·SHA를
  검사한다. 만료/권한 거부/불일치는 실패로 기록한다.
- 시험 프로세스에서만 Release 조회와 패키지 공급을 해당 고정 artifact에 연결한다.
  실제 제품의 설치·백업·팝업·재시작 메서드와 원본 에셋을 그대로 사용한다. 재시작 자식도
  임시 루트를 유지한다. 일반 제품에는 시험 저장소 설정이나 시험 감지 경로를 추가하지 않는다.
- 발견 팝업 → 실제 다운로드 진행 → SHA 검증 → 설치 → 완료 팝업 → 재시작 → healthy를
  클릭하여 검증한다. 호스트 변경과 달리 runtime 변화는 예상 변경으로 기록한다.
  각 단계의 비식별 로그/화면, 원본/복사본 기록·설정·배경 해시를 남긴다.
- 손상 다운로드, 중단, 시작 실패를 반복하여 이전 버전 복구를 확인한다.
  모의 artifact 공급은 공개 Release 실전 전달과 동일하다고 주장하지 않는다.

현재 전환 패키지는 제공하지만 위 온라인 시험 드라이버는 아직 구현하지 않았다.
실제 다운로드→완료 팝업→클릭 재시작 전체 흐름은 pending이다.
healthy 이후 충돌 자동 롤백은 기존 설계에서 지원하지 않는다.
compatibility.json은 pending 유지. main 병합/게시/사용자 설치는 승인 전 하지 않는다.
